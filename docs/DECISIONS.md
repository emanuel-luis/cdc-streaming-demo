# Decisions

Low-impact decisions taken while building the project, with the reason. Newest last.

| # | Date | Decision | Choice | Why |
| --- | --- | --- | --- | --- |
| 1 | 2026-10-25 | Add a second CDC source with `mssql-cdc-pyspark` (SQL Server CDC read by Spark, no Debezium)? | Yes, as the last phase, "two ways to do CDC" | Shows log-based CDC through Kafka Connect and a direct Spark source side by side; it waits until the Debezium path works |
| 2 | 2026-10-25 | Protobuf from day one, or JSON first? | JSON first, Protobuf in its own phase | The first PR proves the pipeline; serialization becomes a contained change with its own contract test |
| 3 | 2026-10-25 | Tooling where the original notes and the engineering baseline differ | Baseline: uv + `pyproject.toml` only (no `requirements/*.txt`), ruff line-length 100 with `BLE`, mypy strict on `src`, Python 3.12, SHA-pinned actions | One set of rules across the portfolio |
| 4 | 2026-10-25 | Package layout | One `src/cdc_demo` package with a `cdc-demo` Typer CLI, `uv_build` backend | One install, one entry point for every container command; no work at import time |
| 5 | 2026-10-25 | Name of the component that writes to Postgres | `mutator` | "Producer" would be confused with Kafka producers, which are the sibling project's subject |
| 6 | 2026-10-25 | Spark runtime | Single container in local mode, built from `python:3.12-slim` + JRE + the `pyspark` wheel, jars resolved by Ivy at image build time | Bitnami images are no longer a free option and a master/worker pair doubles memory for no gain at demo scale |
| 7 | 2026-10-25 | Event identity in the raw log | `event_id = <topic>-<partition>-<offset>` | Deterministic: a replay produces the same ids; a random UUID would not |
| 8 | 2026-10-25 | Exactly-once into Delta with rejects and run metadata | `foreachBatch` writing with `txnAppId` + `txnVersion=batch_id` into the CDC log, the rejects table and the run log | A retried batch is skipped by Delta; rejects and per-batch counts come for free in the same step |
| 9 | 2026-10-25 | Before images | `REPLICA IDENTITY FULL` on `orders` | With the default identity Postgres sends only the key in the before image, so status transitions could not be read from updates |
| 10 | 2026-10-25 | Connector registration | Init container doing `PUT /connectors/orders-connector/config`; DB password read through Kafka's `EnvVarConfigProvider` | PUT is create-or-update, so `docker compose up` can run it every time; no password stored in the connector config |
| 11 | 2026-10-25 | Ports and naming | Compose project `cdc-streaming-demo`, no `container_name`, every host port in `.env` with the usual default, bound to 127.0.0.1 | The sibling `kafka-streaming-lakehouse` also runs Kafka and MinIO; both must coexist on one machine |
| 12 | 2026-10-25 | Ordering key for "latest event per order" (Phase 3) | `(source_lsn, kafka_offset)` | `source_ts_ms` has millisecond resolution and ties when an order changes twice in the same millisecond |
| 13 | 2026-10-25 | Merger watermark (Phase 3) | Last Kafka offset per partition in a Delta control table, moved only after the MERGE commits; MERGE updates only when the event is newer than the stored row | Consumer batches commit in offset order, so an offset watermark never skips rows; the newer-than guard makes a re-run after a crash harmless |
| 14 | 2026-10-25 | How phases ship | One PR per phase, each stacked on the previous branch | The PRs stay reviewable while earlier ones wait for merge |
| 15 | 2026-10-25 | Spark tests | Marker `spark`, deselected by default; run in CI on Linux and locally in WSL or containers | Spark does not run on Windows Python on the owner's machine |
| 16 | 2026-10-25 | Mutator determinism and retries | Sync psycopg, one explicit transaction per mutation, rows picked in Python with an RNG seeded by `(seed, mutation index)`; retry with backoff only on errors before COMMIT; a connection lost during COMMIT stops the run | With a seed and the seeded initial data, two runs make the same changes, retries included; a failed COMMIT has an unknown outcome, and retrying it could apply the change twice and break the manifest |
| 17 | 2026-10-25 | Local object storage (the original notes say MinIO) | RustFS 1.0.3 behind generic `S3_*` settings; SeaweedFS 4.50 as fallback | The MinIO community repo was archived in April 2026 and no `minio/minio` or `minio/mc` image resolves on Docker Hub or quay.io any more; the code only speaks S3 (`s3a://`), so the server is swappable |
| 18 | 2026-10-25 | Versions | Spark 4.2.0 + delta-spark 4.4.1, Confluent Platform 8.3.2 (KRaft only), Debezium 3.7.0.Final from quay.io, Postgres 18.6 | Current stable lines on 2026-10-25; Delta 4.4.1 supports Spark 4.0.1 to 4.2.0 and Debezium 3.7 supports Postgres 14 to 18 |
| 19 | 2026-10-25 | Debezium database user | Dedicated `cdc_reader` role with `REPLICATION` and `SELECT` on `orders`; the publication is created by the owner in initdb (`publication.autocreate.mode=disabled`) | Least privilege: the capture user cannot write to the source |
| 20 | 2026-10-25 | Topic creation | Broker auto-create off; the connector creates `cdc.public.orders` through `topic.creation.default.*` | A consumer subscribing early cannot create the topic with the wrong settings |
| 21 | 2026-10-25 | Schema Registry healthcheck | `python3` one-liner hitting `/subjects` | The `cp-schema-registry:8.3.2` image ships no curl or wget; it does ship python3 |
| 22 | 2026-10-25 | Where the consumer's Protobuf contract lives (Phase 2) | `src/cdc_demo/proto/orders_value.proto` holds the schema the converter registers, verbatim under a header comment; the compiled descriptor set `orders_value.desc` is committed next to it as package data; `grpcio-tools` is a dev dependency only, `make proto` regenerates the descriptor and a unit test fails when the two drift | Spark's `from_protobuf` takes descriptor bytes, so the containers need neither protoc nor a registry call at run time |
| 23 | 2026-10-25 | Confluent wire header in the consumer (Phase 2) | Checked in Spark SQL: magic byte 0 and message index `[0]` (a 6-byte header), payload decoded by `from_protobuf` in `PERMISSIVE` mode; anything else becomes a reject | `Envelope` is the only top-level message of the registered schema, so the serializer always writes index `[0]` as one 0 byte; no Python UDF on the hot path |
| 24 | 2026-10-25 | Raw value in the rejects table once the wire is binary (Phase 2) | `raw_value` keeps its STRING type and holds the base64 of the Kafka value bytes | Protobuf bytes are not text; the rejects table contract stays the same |
| 25 | 2026-10-25 | Schema contract check (Phase 2) | `cdc-demo check-schema` asks the registry whether the checked-in schema can read the latest registered one (compatibility API, `BACKWARD`) and compares both texts after dropping comments and blank lines; `make demo` runs it and fails on any difference | The registry applies its own Protobuf compatibility rules; the text comparison also catches additive changes (a Debezium upgrade adding a `source` field), so the contract is updated on purpose |
| 26 | 2026-10-25 | Proto3 zero values (Phase 2) | Spark's default `emit.default.values=false`: a scalar at its zero value decodes as null | The converter writes nullable columns as plain proto3 scalars, so null and zero share one encoding; no field the consumer reads has a valid zero or empty value (ids start at 1, `amount > 0`, `op` is never empty) |
| 27 | 2026-10-25 | Dependabot PR #3 (Python 3.12 -> 3.15 and Temurin 17 -> 24 in the app image) | Closed; Dependabot ignores Python major/minor, Temurin major and Postgres major updates | The baseline pins Python 3.12 for apps and Spark 4.2 runs on Java LTS lines; a green CI run does not make an unplanned runtime change safe. Patch releases still arrive automatically |
| 28 | 2026-10-25 | Current table shape and deletes (Phase 3) | `current/orders` holds one row per live order: the Postgres columns plus `_source_lsn`, `_kafka_partition`, `_kafka_offset`, `_event_id`, `_op`, `_merged_at`, `_merge_run_id`; a delete event removes the row | "Current" means the rows Postgres holds now; the CDC log already keeps the history and the delete events |
| 29 | 2026-10-25 | Consistent incremental read (Phase 3) | The merger reads the CDC log once, at a pinned Delta version (`versionAsOf`); the deduplicated events and the new watermark both come from that read | The consumer keeps appending; two reads could see different versions, and a watermark taken from the later one would skip rows |
| 30 | 2026-10-25 | First merger run (Phase 3) | The current and control tables are created from explicit schemas (`createIfNotExists`) before the first MERGE; there is no separate first-run path | One code path: an empty target merges like any other |
| 31 | 2026-10-25 | Merge run metadata (Phase 3) | One row per run in `_meta/merge_runs`: run id, UTC times, CDC log version read, events read, distinct orders, rows inserted, updated and deleted (from the MERGE operation metrics), watermark before and after | Same run-metadata rule as the consumer; the metrics show that a re-run changes nothing |
| 32 | 2026-10-25 | How the demo proves the current table (Phase 3) | `make demo` runs `merge` twice, then `cdc-demo verify-current` compares the current table with Postgres row by row on every column and exits 1 on any difference | The second run shows idempotency on real data; the row-by-row comparison is the phase's done criterion |
| 33 | 2026-10-25 | Engine for the analytics layer (Phase 4) | dbt-duckdb reading the Delta tables in place with DuckDB's `delta` extension; no Spark and no copy of the data | The marts are small aggregates; a second Spark session would cost 2 GB and a minute of startup for no gain, and DuckDB reads deletion vectors, column mapping and checkpoints |
| 34 | 2026-10-25 | Versions (Phase 4) | duckdb 2.0.x, dbt-core 1.12.x, dbt-duckdb 1.11.x, streamlit 1.66 or newer, in an `analytics` extra; Dependabot ignores dbt and DuckDB minor and major bumps | They are tested together; the stack moves as one set on purpose. DuckDB 2.0.0 is days old, so the fallback is duckdb 1.5.x with the same models |
| 35 | 2026-10-25 | protobuf cap (Phase 4) | Dev group `protobuf>=6.33.5,<7` and `grpcio-tools>=1.80,<1.83`; Dependabot ignores the newer lines | dbt-common and dbt-adapters need protobuf below 7, while grpcio-tools 1.83 and later need protobuf 7. Only the dev group is affected; the committed descriptor still matches (unit test) |
| 36 | 2026-10-25 | DuckDB extensions in the image (Phase 4) | `httpfs` and `delta` are installed and loaded at build time, as the app user | Containers need no internet access at run time, same rule as the Ivy cache in the spark image; the LOAD at build proves they match the installed DuckDB |
| 37 | 2026-10-25 | How DuckDB addresses the lake (Phase 4) | `s3://` paths built from `LAKE_ROOT` by `LakeSettings.duckdb_root`, path-style URLs, an S3 secret from the same `S3_*` variables | DuckDB ignores secrets for `s3a://` (Hadoop's scheme); the endpoint is the same RustFS service, so only the scheme changes |
| 38 | 2026-10-25 | Spark-side changes for DuckDB (Phase 4) | None: no Delta table properties or writer settings were changed | The delta extension reads what Delta 4.4 writes today; if a read fails, the fix is a table feature decision with its own entry |
| 39 | 2026-10-25 | Who creates the consumer's tables (Phase 4) | The consumer creates the CDC log, rejects and `ingest_runs` from their schemas at startup, partitioned like the writer; the create helper is shared with the merger | The rejects table used to appear with the first reject, and a dbt source on a missing table fails the build. Touches the consumer, so it has its own Spark test |
| 40 | 2026-10-25 | Publishing the warehouse file (Phase 4) | dbt builds into `analytics_build.duckdb`; after `dbt build` passes the file is checkpointed and renamed over `analytics.duckdb`; a failed build leaves the published file alone | The dashboard never sees a half-built or failing warehouse, and only one process writes the file. DuckDB allows one writer, so the dashboard opens it read-only per query |
| 41 | 2026-10-25 | Model layout (Phase 4) | Schema `staging` holds one view per Delta table (`stg_lake__*`, no `raw_value` from rejects); schema `marts` holds four tables with enforced contracts: `dim_orders_current`, `fct_order_status_changes`, `fct_order_activity_hourly`, `fct_pipeline_runs` | Views cost nothing and keep the lake as the source of truth; contracts make a column or type change fail the build instead of the dashboard |
| 42 | 2026-10-25 | Reconciliation inside dbt (Phase 4) | A singular test recomputes the current table from the CDC log (latest event per order by `(source_lsn, kafka_offset)` among events at or below the merge watermark, deletes removed) and compares with EXCEPT both ways | It checks the merger against an independent computation in a different engine; the watermark bound keeps it valid while the consumer keeps appending. A build between the MERGE commit and the watermark commit can fail it, and the demo runs the steps one after another |
| 43 | 2026-10-25 | How the demo proves the marts (Phase 4) | `make demo` ends with `build-marts` and `verify-marts --manifest`: event counts per op, rejects and live orders in the marts must equal what the mutator reported | Same manifest as the lake check, so one workload is asserted at every layer |
| 44 | 2026-10-25 | Dashboard (Phase 4) | A thin Streamlit page: four KPIs, status chart, hourly activity, recent status changes, latest runs; read-only file volume, no auto-refresh, a build-time caption, an info message when the file is missing | Everything shown comes from the marts, so the page proves them without logic of its own; a manual reload after `make marts` is enough for a demo |
